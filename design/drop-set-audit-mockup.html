Spotter · audit + proposal

The drop set is two thirds of
a feature: the chain joins nothing,
and the ghost column drifts.

data/superset.ts is right and so is the rest-on-tick predicate — a tick earns a rest only when nothing is queued to be taken immediately after it works exactly as written, for drops and for pairs. What is wrong is on either side of it. The connector that was meant to say these two were one effort was built as half a drawing and aimed at the wrong column; the explanation leaves the instant you tick; and three writers downstream — lastLog, saveAsRoutine, logSet — count a drop as an ordinary set and quietly corrupt what they hold.

What is actually broken
  • Next week's "last time" column shifts by one for every drop you ever took. finishSession writes every ticked row into lastLog; sessionFrom reads it back last[k], index for index. Drop off set 2 of 4 and set 3's ghost becomes the drop's 50 × 8. lastMarks is built off the same array, so prevMark and LastNotes' "set 3" name the wrong rows too.
  • Saving a day as a routine bakes in the drop weight. saveAsRoutine and saveDayAsRoutine both take sets: e.sets.length and read their numbers off the last ticked row — which is the drop. A 3 × 65 kg day saves as 4 sets @ 50 kg.
  • A drop can be logged as 65 × 0. The new row arrives with the weight prefilled and prev: '—', and logSet's guard is !cur.w && !cur.reps — so the prefill defeats it and there is no ghost to fill the reps from. That is the exact "BW × 0 … next session's last-time lie" the tick refuses everywhere else.
What is unfinished rather than wrong
  • The chain is half of its drawing. The mockup's connector is an L — a riser in the gutter plus a stub into the digit. Only the riser was built.
  • And it is aimed at one digit at a time. chainRiserLive moves it to left: 16 to follow the live box's 9px inset, but the digit above is still at 8. Live or not, it lines up with one of the two rows it is joining and misses the other.
  • A ticked drop is indistinguishable from a set. queued — Drop from set 3 — no rest — only renders while the linked row is live. Scroll back afterwards and rows 1–6 read as six identical sets. The diary shows ↳; the ledger, where the decision is actually made, shows less than the record does.
  • The button never says "drop set". L.addDrop — + Drop set / + Dropsatz — is written in both languages and referenced nowhere; the button carries holdAddDrop instead, and two long Hold to… labels now share a strip that used to hold one at full width.

  • The ↳ is not new vocabulary — it is the diary's, brought forward one screen. plan.tsx already folds a drop into the set it came off with ↳ 50 × 8. The same glyph in the ledger means the session and the record say one thing in one character, which is the rule the app already follows for addOnlyMissing and for the tip strings the tour reads.
  • It goes in the ghost cell because that cell is empty by decision, not by accident. A drop is written with prev: '—' — last week's set N+1 was not this drop, and a figure that isn't about this row is worse than none. So the column is guaranteed free on exactly the rows that need a marker, and a lone ↳ makes no claim about last time: it terminates a line drawn from the row above.
  • It survives the mark. The whole reason the chain went in the gutter is that the index digit belongs to SetMark — judge a drop and its verdict would erase the fact that it was one. The elbow and the ↳ are both outside the digit, so both survive a ▲.
  • And it survives the tick, which the wait line does not. This is the part that makes a finished session readable: the elbow and the glyph are row furniture, not wait furniture, so they stay behind when queued leaves with the live box.
  • One x-coordinate for both states. Dropping chainRiserLive's left: 16 is what makes the riser hang from the digit above in every case; the live box's 9px inset is then absorbed by the elbow's horizontal run instead of by moving the vertical. The line visibly steps in because the row it enters is inset — which is true, and reads as structure.
  • Weight goes to accent600, one step up. As shipped the riser is at the live border's weight and a third of its length; at 1px in a 3px gap that reads as an artifact. The elbow is long enough to read as a line, so it can afford the step — and needs it to stay visible over the accent wash behind the live box.

3 · The ghost column, next Tuesday

The visual half is cosmetic. This one is not: a drop taken anywhere but the last row shifts every "last time" figure below it, permanently, for that exercise.

broken
finishSession writes lastLog[e.ex] = { date, sets } from e.sets.filter(x => x.done) — drops included. sessionFrom then reads last[k] index for index. The two arrays stop describing each other the moment a drop is not last, and lastMarks shifts with them.
Today · Bench Press, drop off set 2 Stored in lastLog Next Tuesday's ghost Should be
set 1   70 × 8 "70 × 8" set 1 → 70 × 8 70 × 8
set 2   65 × 6 "65 × 6" set 2 → 65 × 6 65 × 6
set 3   50 × 8  ↳ the drop "50 × 8" set 3 → 50 × 8 60 × 6
set 4   60 × 6 "60 × 6" set 4 → 60 × 6 60 × 5
set 5   60 × 5 "60 × 5" never read (routine asks for 4) —
  • The fix is one filter, in one place, with no shape change. lastLog is not the diary — it holds only the latest session per exercise, because that is all a ghost needs. A drop is a fact about the day, and the day already keeps it (LoggedExercise.links), so the ghost has no business holding one: build lastLog's sets and lastMarks from ticked.filter(x => !x.link) while history keeps the full ticked array. No STORAGE_VERSION bump and no migration — the stored shape is identical, only shorter.
  • The same one-line rule for the two routine writers. saveAsRoutine and saveDayAsRoutine both take sets: e.sets.length and read their numbers off the last ticked row. Counting and reading over the unlinked rows only fixes both: a routine has no way to hold a drop (RoutineItem.with has no drop twin, by decision), so a drop must not survive into one as an ordinary set — and above all its weight must not become the routine's.
  • And a drop must not be tickable empty. logSet's guard assumes a row carrying a value in w carries one in reps too, which every other row earns from its ghost. A drop has no ghost and arrives with w prefilled, so the guard passes and 65 × 0 is written. Keep the prefill — editing 65 down to 50 is one sweep of the number drag, which is what the cell is for — and widen the guard to refuse a tick that would leave either field at zero with nothing to fill it from.

Not proposed, and why
  • Sub-numbering (3a / 3b). Still the clearest thing to read and still wants the one slot SetMark has already spent — turned down in the original mockup for that reason, and nothing here changes it.
  • Hiding drops from the n / m chip. Six sets were lifted. The count is right; only its legibility was missing.
  • A planned drop on a routine row. Drawn and turned down once already — it has to invent a weight, which is the one thing a plan is not allowed to write over your own history.
  • Blanking the drop's weight instead of prefilling it. It would close the × 0 hole for free, and it costs the thing the row is for: 65 → 50 is one sweep of the number drag. Fix the guard, keep the gesture.
  • A tip. + Drop set is a labelled control and fails the admission test — could a careful person use the app for a month and never find it? No.
