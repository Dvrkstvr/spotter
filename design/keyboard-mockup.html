Inputs above the keyboard

The app asks Android to shrink the window when the keyboard opens (softwareKeyboardLayoutMode: "resize") and the session screen's own comment relies on it — SDK 54 runs Android edge-to-edge unconditionally, and under edge-to-edge that mode is a no-op. The keyboard now draws over an app that did not move, and whether a field survives is an accident of where it sits. The fix is not per-screen: every input in the app reaches the glass through one of two shells — Sheet and the session's FullScreen — plus Screen for the tabs. Keyboard avoidance lands in those shells once, in plain JS, and every field inherits it. Below, each surface as it fails today and as it behaves with the shells doing their job.

  • The header stays; the ledger gives. Kicker, progress and the exercise name are flex-none — only the scroll area shrinks, so you never lose which exercise and which set you're on.
  • The CTA above the keys is restored behavior, not new behavior. The comment at the top of session-overlay.tsx promises exactly this; it went quietly false when SDK 54 made resize a no-op.
  • The scroll-into-view comes free. Once the container genuinely shrinks, Android's own focused-field behavior scrolls the row visible — the same mechanism that made adjustResize work before edge-to-edge. No scroll-to code of ours.

Mechanics — settled if we build this
  • Where it lands: KeyboardAvoidingView (behavior="padding") wrapped inside the two shells — Sheet / FullScreen in sheet.tsx — and in Screen for the tab-level search fields. No per-screen code; the session overlay's stale comment gets rewritten to name the new mechanism.
  • Pure JS, so Expo Go keeps working. No react-native-keyboard-controller: it is a native module, which would mean the optional-bridge treatment, a dev-build rebuild and new APKs on both phones — for behavior the built-in component covers.
  • One honest wart: Android only reports the keyboard after it is up (there is no will-show event), so content moves a beat behind the keys. Every JS-side approach shares this; the native module is the only cure, and it is not worth its cost here.
  • Nothing durable is touched. No store state, no PERSIST key, no STORAGE_VERSION — this is layout only, and app.json keeps resize for the day Android honors it again.
