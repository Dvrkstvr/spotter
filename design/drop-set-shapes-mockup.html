Spotter · session ledger

A drop set should not be drawn as the next set

The three options in the audit were one option: a connector in the gutter, at three lengths. None of them read, and the reason is structural rather than a matter of taste — a drop is drawn with exactly the same row as a working set, so a line pointing at it is arguing against everything else on the row. These four start from the row instead.

The thing under the complaint
  • A drop takes a set number. The index cell renders index + 1 — the raw row index — so a drop off set 3 draws as 4, and the working set after it draws as 5. A four-set exercise with one drop counts to five in its own ledger, and the count is wrong for the rest of the workout.
  • So the row is not merely un-marked, it is mis-marked. Every option below begins by taking that digit away. That single change is most of what makes a drop look like a drop, and no connector can do it.
  • The diary already knows this — plan.tsx folds a drop into the set it came off with ↳ and keeps the count at 4 sets. It is the live ledger that disagrees with the record.

A · The whisper cheap

Same grid, less of everything. A drop is what happened after the set, so it is printed like a footnote to it rather than entered like an entry of its own.

No digit, no ghost figure, a shorter rule under each number, 12.5px instead of 15, a smaller tick at accent600 rather than accent. The word drop sits where "last time" would be — a cell that is empty on a drop by construction, since last week's set 4 was not this drop.
  • It reads at a glance and it costs almost nothing. One style object, one conditional in the index cell, no geometry change: the column centres all hold, so inputW / flyDx / inputCatch are untouched.
  • Weight is the right axis for this. The app already uses it — the mark's glyph dims from accent to neutral500 in the diary, a pair's hairline steps down to accent800 there. Quieter means subordinate here already.
  • But a live drop has to be loud. This is the whole objection: the row you are about to lift into needs thumb-sized figures and a hittable tick, so the whisper can only apply once the row is done. A shape that changes on tick is a shape you learn twice.
  • The word drop is a fifth string in the ledger, and it needs a German twin (Drop is what a German gym says, so that one is free).

B · The spine cheap

A bracket alongside, not a pointer at. Two pixels down the left gutter, running the height of every row hanging off one set — the blockquote convention, and the app's own vocabulary for these belong together.

The drop keeps its full-size row — it is a set you lifted and may still be standing in — and loses only its number. The bar is pairRule, the style the superset already draws down the side of its two halves: width 1, accent700, rounded. It runs alongside rather than pointing, which is what stops it reading as the stray tick the riser reads as.
  • It is the superset's own drawing, one scope down — the same style object, not a lookalike. Both features mean these were one effort; drawing them two ways would be two languages for one statement, and the diary already dims the same bar to accent800 for a pair, which is the step this could borrow too.
  • The variant worth arguing about: bracket the group, not the drop. A superset's bar runs down both halves, so the exact analogue starts at the parent set and ends at the last drop. It reads better — the bar then says which set the chain came off, instead of leaving adjacency to say it — and it costs one look-ahead (sets[j + 1]?.link) plus the same 9px on the parent row, which puts a visible jog in the number column. Drawn here the narrow way; the wide one is a one-line change either direction.
  • A chain is free. 65 → 50 → 40 is three rows under one spine, with no sub-numbering and nothing to invent. Each drop draws its own segment overlapping the gap above it, so the bar is continuous without anyone owning the whole group.
  • It survives the mark and it survives the tick. The spine is left of the index cell, so a verdict can take that cell without erasing the fact that the row was a drop — the exact collision the gutter riser was invented to dodge, solved by moving 2px further out instead of hiding between rows.
  • Live and done are the same drawing. Only the spine's bottom moves, to clear the live box's radius. Nothing about the row changes shape when it is ticked, which is what A cannot promise.
  • Cost: one absolutely-positioned view and 12px of left padding on the row, with the same 12 taken off the right margin so the tick column and both number columns stay where they are.

C · The stack expensive

One set, two lines, one digit. Set 3 becomes a block that contains both efforts. The count cannot drift, because the drop is never a row in the first place.

A faint container at wash.text(8) holds both lines with a hairline between them; the digit belongs to the block, not to either line. This is sub-numbering without the sub-numbers — the clearest thing to read in the original mockup, minus the collision that killed it.
  • It is the only one that makes the count structural. The others take the digit away by decision; here there is no digit to take, because a drop is never a numbered thing. Nothing can put it back by accident.
  • And the only one that survives a marked drop cleanly — the drop line has no index cell at all, so a verdict on it needs somewhere new to live. That is a genuine open question, not a solved one: probably the same slot as the working line's, indented.
  • The cost is that a row stops being a row. SetRow, the live box, the drag cells, the mark sheet's markAt.j and the reorder pitch are all written per row over a flat list. The arithmetic underneath (liveJ, logSet, roundOf) indexes into sets and would not change — this is a rendering change all the way down, but it is a deep one.
  • And the live state is awkward. When the drop is the row you are lifting into, the block has to raise one of its two lines to thumb size and leave the other at rest, or raise the whole block and take up a third of the screen. The live box is currently a wrapper around one row; here it would have to be a wrapper around part of a block.

D · The delta cheapest

Say what fell. The row keeps its shape and loses its digit; the ghost column — empty on a drop by construction — carries the one fact a drop set is actually about.

−15 kg at accent400, where — sits today. The only option that adds information rather than only adding shape: the others say this is a drop, this one says this is a drop of fifteen kilos, which is what you would want back in six weeks.
  • Nothing moves. Two text substitutions and a colour. No new view, no geometry, no new string that needs a German twin — a number and a unit the app already formats.
  • And no arrow, which is the part worth knowing. The obvious drawing is a ↓ in the index cell — and MARK_D.down is a down arrow, drawn at accent400 in that exact cell for go lighter next time. Two down arrows meaning two things, and a drop that carries the verdict showing one arrow for both. The minus sign already says which way it went, so the arrow is what gets cut.
  • It fills a cell that is guaranteed free. A drop is written with prev: '—', because last week's set 4 was not this drop. So the column is empty on exactly the rows that need something to say.
  • The wrinkle: a live drop has nothing to report yet. A drop arrives carrying the weight it came off (w: src.w || g.w), so the delta opens at −0 kg, which is worse than blank. It would have to draw the bare ↓ until the figure actually differs — a small rule, but a rule.
  • And as a shape it is the weakest. Scanning the ledger from across the gym, the row still has a row's outline. This is the option to combine, not the option to ship alone.

E · B + D, which is what I would build

The spine is the shape and the delta is the fact, and they occupy different parts of the row — nothing about them argues. Three states: the drop live, the drop sealed with a working set under it, and a chain of two.

Live — the drop is the set you're in
The spine runs inside the live box's own padding, at the same x it keeps on a sealed row. The index cell is empty and the ghost column holds the delta as soon as there is one; the wait slot carries the existing no rest line.

  • The delta on the second drop is measured from the top of the chain, not from the row above it. −25 rather than −10: what you want to know at 40 kg is how far you have come down from the working weight. The row above is visible on the same screen and the subtraction is not the point.
  • Every option here removes the digit, and that alone changes what the ledger counts. Nothing downstream reads it — the index is rendered from index + 1 and used nowhere else — but the accessibility label is built from the same number (L.setLabel), so a drop needs a label of its own or a screen reader will keep calling it set 4.
  • None of this touches the data. link?: true on LoggedSet is already the whole model, the delta is derived from the weight of the row the chain hangs from, and the spine is derived from adjacency. No new field, no STORAGE_VERSION bump, and nothing new crosses to a buddy.
  • The diary needs no change under B or D — it already folds a drop into its parent with ↳ and already counts 4 sets. Under C the ledger would finally match it, which is an argument for C that the cost has to be weighed against.
