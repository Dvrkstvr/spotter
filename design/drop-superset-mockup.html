Spotter · mockup

A drop set and a superset are
the same missing sentence:
this one doesn't earn a rest.

Both are already representable. A drop set is a set at a lower weight taken straight away — add a row, type 50, tick it. A superset is a set on the other machine taken straight away. What the app gets wrong in both cases is the rest: every tick starts restSeconds, and a three-minute countdown is the precise opposite of what either of these things means.

So the rule underneath both is one sentence — a tick earns a rest only when nothing is queued to be taken immediately after it — and the two features are the two ways something can be queued: the next row of this ledger, or the paired exercise's row in this round.

Settled
  • Drop sets are made in the moment, supersets only in the routine. A drop is a decision about how that set went, which nobody makes a week early; a superset is a decision about which two exercises, which is exactly what a routine holds. There is no mid-session pairing anywhere — not in the overview sheet, not on the exercise screen.
  • A superset draws both exercises on one screen. Two ledgers bound by one hairline, one live row across the pair, and the round is the thing that advances. §4.
  • One exercise per screen becomes one unit per screen. A pair is one swipe stop, one chip position, one bracket in the overview. That is the whole cost of the decision, and it is paid in s.active meaning "which unit" rather than "which exercise".
  • The chain is drawn between digits, never in one. The index column belongs to SetMark — the mark takes the digit's place. A hairline in the gutter between two rows can never argue with it, and the pair's bracket is the same grammar one level up.
  • Additive, so no version bump. One optional field on a session set, one on RoutineItem, two on LoggedExercise. STORAGE_VERSION stays 4.

The gutter link, in the editor
Unpaired gaps carry a dim glyph; the paired one lights and labels itself. Adjacency, not a group id — which is what the editor already is, so a drag breaks the pair by itself and a giant set is just two links in a row.

Why not
  • A planned drop has to invent a weight, and the app already refuses to let a plan write a number over your own history.
  • Two controls per editor row, for a thing decided at the bar.
  • It would have to reach a buddy, and their 50 kg is not yours.
Which is the asymmetry
  • A superset is which two exercises — a template fact, so the routine owns it and there is no mid-session pairing.
  • A drop is how that set went — a session fact, so the session owns it and the routine never mentions it.
  • An orphan link is nothing. A with on the last row, or on a row whose neighbour was deleted, resolves to no pair — read at the point of use, never stored-and-swept, exactly as a plan entry naming a deleted routine is handled by the plan screen rather than tidied away.
  • The pair travels with the routine. It is a field on RoutineItem, so a buddy's copy, a backup, an upsertShared and the coach's import all carry it with no new code — and mergeRoutine keeps yours, the way it keeps your numbers.
  • The three seeded routines gain no pairs. A superset is a choice about how you like to train, and shipping one inside Chest A would be the library making it for you.

  • The round is derived, never stored. It is the lowest set index that isn't ticked in either half — the same "first unlogged row" arithmetic the plan already uses to decide what next means, one scope down. Nothing new is persisted and nothing can drift.
  • The heading is the pair, and the highlight is the half. Incline Press + Cable Fly stays put; the live half's name goes accent200 and the other stays neutral300. The name never moves, so you always know what unit you are standing in, and the colour tells you which machine to walk to.
  • Every rule inside a half is untouched. The scrub, the ghost, the note line, the mark sheet, + Add set, + Drop set — a drop set inside a superset half is just a linked row, and needs no thought at all. The two features nest rather than interact.
  • The buttons belong to the half, not the pair. They are drawn under the live half only, which is also the half you could be adding a set to — two sets of them permanently on screen would be four held buttons for one unit.
  • Uneven set counts just run out. Three sets against four is three full rounds and then a fourth with one half empty; the round arithmetic already says so, and the last set earns an ordinary rest because nothing is queued behind it.
  • The screen scrolls, and that is the price. Two ledgers with the note line under every row do not fit a phone. The rule that the way in never disappears is worth more than the scroll — it was the whole argument for putting it on every row — so nothing is conditionally hidden here.

  • The buddy protocol needs nothing. BuddyProgress.list carries done booleans per set; a chain is still rows and a pair is still two list entries, so their counts still read. Whether the link travels changes only how their turn is computed, and an older build that never sends it simply hands over one set early — degraded, not broken, which is the bar every protocol addition here has cleared.
  • Every rest rule already holds. restLeftOf is untouched; what changes is one condition at the site that writes rest on a tick. The alarm's cancel path is the scheduling effect's cleanup, which already covers "the rest ended for any reason".
  • The statistics are unaffected. keyLifts reads the top set, so a drop at 50 can't be mistaken for a lift going backwards; volume is each entry's own vol, and a drop set is honest load volume. Balance reads groups, and a pair is still two exercises filed where they always were.
  • Finish still holds while sets are open — a linked row and an unfinished round are open sets like any others, and an untouched drop is exactly the thing you might want to walk away from.

7 · The shape

Four optional fields, each additive inside a key that already exists — the same argument that let marks, list, secs and vol land without a migration. STORAGE_VERSION stays 4. 

// src/data/exercises.ts — the pair is a routine fact, and only a routine fact
export type RoutineItem = {
  ex: string; sets: number; reps: number; w: number; planned?: true;
  /** Supersetted with the item after it. Adjacency, not a group id: the
      editor is a flat reorderable list, so a drag breaks the pair by
      itself and a giant set is two links in a row. An orphan — last row,
      or a neighbour since deleted — resolves to no pair where it is read,
      never swept. */
  with?: 'next';
};

// src/store/workout-store.tsx
export type LoggedSet = {
  w: string; reps: string; done: boolean; prev: string;
  mark?: SetMark; note?: string; prevMark?: MarkNote | null;
  /** This set continues the one above it: taken straight after, so the
      tick on that one earns no rest. A drop set — made in the session and
      never planned, which is why nothing like it exists on RoutineItem. */
  link?: true;
};

/** Flat, as it always was: a pair is two entries that happen to be joined.
    `progress.list`, `removeSessionEx` and the overview all keep reading a
    list of exercises; only the screen groups them into units. */
export type SessionExercise = { ex: string; sets: LoggedSet[]; with?: 'next' };

// the diary's copy, index for index with `sets` — same relationship
// `marks` already has, and kept in step for the same reason
export type LoggedExercise = {
  ex: string; sets: string[]; marks?: (MarkNote | null)[];
  links?: boolean[]; with?: 'next';
};
  • One sentence decides every rest. Is anything queued straight after this set? — the next row of this ledger when it is linked, or the paired half's row of this round. One predicate at the one site that writes rest, and both features fall out of it.
  • The session list stays flat. Grouping is computed where it is drawn, so nothing that already walks session.list — the buddy diff, the overview, the ×, the totals — learns a new shape.
  • Backups and merges need no change. Both fields ride inside keys that already move whole: history keyed by historyKey (date / rid / name / secs / vol, so neither can split one session into two) and routines through upsertShared.

9 · Where it lands

Files
  • src/data/exercises.ts — RoutineItem.with.
  • src/store/workout-store.tsx — LoggedSet.link, SessionExercise.with, addDropSet, the rest-on-tick predicate, the turn count over chain heads, sessionFrom carrying the pair, finishSession writing links / with.
  • src/components/overlays/routine-overlay.tsx — the pairing gutter between rows.
  • src/components/overlays/session-overlay.tsx — the chain riser, + Drop set, the sheet's switch, the paired screen and its round arithmetic, the overview's bracket.
  • src/app/(tabs)/plan.tsx — the joined figure and the logged pair's bracket.
  • src/data/i18n.ts — nine strings, both languages.
  • STORAGE_VERSION stays 4. Nothing migrates.
Deliberately not built
  • Rest-pause, cluster sets, myo-reps. Every one of them is the same field with a different rest between the halves. If link ever needs a duration it is link?: number — seconds — and true means zero. Additive again; wait for someone to ask.
  • A per-chain or per-round total. Already in the session's volume, and a second figure beside the rows would be the summary's one number said twice.
  • Circuits — three or more exercises with one rest at the end. with: 'next' repeats, and the routine editor would draw it with no new code; what does not survive is the paired screen, which is sized and worded for exactly two. A third half is a third screen decision, not a longer bracket.
  • A tip for either. Both are reached through labelled controls — + Drop set, and a routine you paired yourself. The admission test is whether a careful person could use the app for a month and never find it, and neither can hide.
