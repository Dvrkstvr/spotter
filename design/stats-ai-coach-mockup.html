Spotter · design mockup · 11 Aug 2026

Stats & AI Coach

A read of the diary the app already keeps — strengths and weaknesses drawn from logged sets over time — and a loop that turns it into recommendations. It opens from a card on the You tab: pick a goal, Spotter writes a prompt around your data, you hand it to any AI chat, and paste the answer back. The answer carries a machine-readable block and its own way home, so the app can preview and import the recommended exercises and routines. Later, a tiny on-device model replaces the copy-paste hop; every screen after the prompt stays the same.

01

The way in — a card on You

  • The card sits under the profile header, above Buddy — the greyed sections are today's You screen, untouched. No sixth tab.
  • It wears the hero gradient (t.heroGradient, accent-900 → surface at 62%), the same treatment as Today's hero — the one card on the screen that leads somewhere big.
  • The headline is computed, not canned: the largest deviation from an even split (or, when balance is fine, the current streak). The card earns its tap by saying something true before you take it.
  • The mini bars are the radar's data at a glance — six groups, weak ones dimmed. One tap opens Insights (02).
  • Until ~5 sessions are logged the card shows a quiet empty state ("Log a few workouts and your stats appear here") and the coach flow stays hidden — no recommendations on no data.
02

Insights — what the diary already knows

  • Everything on this screen is derivable today — from history (sets, volume, dates, duration), lastLog (latest numbers per exercise) and each exercise's muscle group. No new logging, no new persisted state.
  • The radar is the headline; the ranked weak-point rows are the honest version of the same fact and are what the prompt actually uses. Cardio is detected through the distance/duration measures, not a muscle group.
  • Volume counts load sets only, same gate as totals() — kilometre-minutes stay out of the kg number, so the chart never lies.
  • Favourites are counted, not chosen: the exercise appearing in the most logged sessions, the routine with the most history entries — by the name frozen at log time, so a renamed routine keeps its record.
  • Fun facts are unit-aware: load volume maps to weights (cars, a 747), logged distance to geography (the Sahara line goes here the day a run is logged). One curated comparison list, deterministic pick per month — the same fact all month, a new one next month.
  • Set verdicts (lastMarks — a stalled squat marked "lighter" twice) feed the weak-point read: a lift you keep down-marking is a weakness the share-of-sets numbers can't see.
03

Goal — one pick, a few dials

  • Goals are radio chips (the Chip component, radio semantics like everywhere else). "Fix weak points" is pre-selected when the data shows any — the screen states its reason in one line.
  • The equipment row is seeded from kinds — the user's own list, renames included — so the AI plans with gear that exists in this person's library.
  • Privacy is a visible switch, not a policy page: each data block the prompt will contain is a row you can untick. Profile is off by default; age and bodyweight are the only personal numbers anywhere in the flow.
  • Selections persist as one small settings object, so re-running the coach next month is two taps.
04

Prompt — readable by you, parseable by them

  • The prompt is shown in full, not hidden — it is exactly what leaves the phone, which is what makes the privacy toggles on the previous screen honest.
  • It ends with the reply contract: rule 2 makes the AI close its answer with one fenced ```spotter block in a fixed JSON shape. Everything before the block is prose for the user; the block is for the app.
  • Rule 3 makes the answer carry its own way home. The AI ends with "copy this entire message → open Spotter → paste", so whoever wandered off into a chat app gets walked back to the Import screen by the reply itself — no memory of the flow required.
  • The exercise list at the end tells the AI what already exists (from allEx()), so recommendations reuse the library instead of inventing "Flat Barbell Chest Press" beside Bench Press.
  • Export is a plain Android share intent — no API keys, no accounts, works with whichever chat app is installed. The on-device model later slots in exactly here and answers the same contract.
  • The dashed CTA borrows the app's waiting-state grammar: the loop isn't done — it waits for an answer to come back.
05

Import — preview first, additive always

  • Paste the AI's whole reply — the parser finds the one ```spotter block and ignores the prose around it. No block, or broken JSON → one plain error line, nothing half-imported.
  • Preview before anything is written. Every routine is a card you can untick; every exercise row says whether it matched the library (case-insensitive, against allEx()) or will be created as a custom exercise.
  • Import is additive only — new Routine and Exercise entries through the existing store shapes. It never edits or overwrites what's there, and history / lastLog are untouchable by design. Re-importing the same answer dedupes to zero.
  • Measures come through the contract (load / time / distance / duration) — fixed at creation, like every exercise. The plank imports as time, the row as duration, and the AI's numbers land as the routine's plan (planned), so the first session opens with them pre-typed — same rule as a routine you typed yourself.
  • Anything unresolvable degrades loudly but small: a wrong equipment name files under Other with a one-line notice, never a silent guess.

The contract

One JSON shape, two producers

  • Names are the join key — the AI talks names, the app resolves them to ids on import. New names become custom exercises with the name filed under the current language (LangMap), like any hand-made one.
  • kg/reps follow the measure the way the whole app does: for time, reps means seconds; for distance, kg means km; duration is minutes and nothing else.
  • The same contract later becomes the on-device model's output format — the preview screen, matching and import path don't change, only where the answer comes from.

Open questions

  • Radar vs. bars only — the radar is glanceable but shape-sensitive to axis order; if it misleads, the ranked rows alone carry the screen.
  • 1RM estimates — "best set" is shown; estimated 1RM trends are a nicer strength signal but imply a formula (Epley et al.) we'd have to stand behind.
  • Fun-fact comparisons — one curated, unit-aware list (weights for kg volume, geography for km). Needs a tone pass so an off week never reads as mockery.
  • German — the prompt should be authored in the user's language; the contract stays English-keyed either way.
